Developing

Writing a module

A module is how EiN learns to do something new: its commands, pages, background services, settings and pipelines come in one folder that you can install on any EiN. This page is for developers. It walks through a small module from its first file to publishing it, and shows where each kind of part goes.

What a module is

A module is a folder with a mod.json at its top, kept in a repository of its own named module-<name>. Core knows no module by name: the Archive, the Assistant and the media service client, ems (The media service), are modules like the one you write, and you can read their repositories to see any part on this page at full size.

When EiN sets a module up, it finds most of what the module brings by where it is in the folder. The manifest says who the module is, what it shares with other modules, and what it adds to machinery core already has. Nothing in the manifest is code.

In the module What EiN does with it at setup
mod.json Reads and checks it; refuses the module when it is wrong
bin/ Adds the folder to every shell's PATH; each file is a command, in bash or TypeScript
services/<name>/ Registers and enables a background service: start.sh with a config.json; a single script services/<name> is wrapped in a folder of its own
pipelines/*.yaml Registers each pipeline definition
ui/ Bundles the pages mod.json names; links ui/nav.json as the module's sidebar and top-bar entries
ui/index.html Links a built ui/ as a site of its own, /var/www/<name>
etc/config Links it as /etc/config.d/<name>: the module's own choice of settings
etc/<x>.d/ Links it as /etc/<x>.d/<name>, for the module that reads that folder; mod install restarts the services that read it when it changes (dropIns)
etc/ (anything else) Copies it into /etc when it is not there yet; never overwrites
lib/, types/, test/ Nothing; ordinary source, reached through the manifest's imports and exports
uninstall.sh Runs it when the module is removed

The module manifest describes every field of mod.json. This page uses the few a first module needs.

Before you start

You need:

  • An EiN you are the administrator of, to install the module on while you work. A test installation is better than the one holding your family's archive.
  • A place for the module's files that you can edit, on the machine EiN runs on.
  • For publishing, a repository on GitHub, Forgejo or Gitea.

You do not need a copy of EiN's source to write a module: EiN bundles a module's pages and runs its TypeScript itself. To type-check a module and run its tests you work inside a checkout of core, which Building from source sets up.

There is no command that makes a new module for you. Start from the folder below, or copy a small published module such as module-ems and cut it down.

Lay out the module

This page builds recipes, a module that keeps the Wrenfield family's recipes as nodes under /archive/recipes, with a command to add one, a command to list them and a page that shows them:

module-recipes/
├── mod.json
├── bin/
│   ├── recipe-add          a command in bash
│   └── recipe-list         a command in TypeScript
├── ui/
│   ├── nav.json            its sidebar entry
│   └── pages/
│       └── recipes.tsx     its page
└── docs/
    └── index.md            its guide

The module's name is lower case, digits and hyphens. It is the folder's name under /usr/modules, the owner EiN shows beside its commands and settings, and the prefix of its import aliases (@recipes/…).

Write the manifest

Start mod.json with who the module is and the core it is written for:

{
  "name": "recipes",
  "version": "0.1.0",
  "description": "The family's recipes: who cooked what, for how many",
  "author": "Ruby Wrenfield",
  "license": "MIT",
  "coreApi": "^0.6.0",
  "roots": ["/archive/recipes"],
  "nodeTypes": [
    {
      "type": "recipe",
      "label": "Recipe",
      "category": "content",
      "root": "/archive/recipes",
      "description": "One dish: its title and how many it serves."
    }
  ],
  "ui": {
    "routes": { "/recipes": "ui/pages/recipes.tsx" }
  }
}
Field What it does here
name The module's name; it must match the folder it is installed in
version Its semver version, which other modules' dependencies ranges are checked against
description One sentence for mod list, Settings → Modules and the documentation
coreApi The range of core's module API the module is written against; mod setup refuses it when this core does not satisfy it
roots Folders under /archive the module's content lives in; setup creates a missing one and nothing ever removes one
nodeTypes The node types it defines, for the documentation; one with a root is what an @ in the search box completes to
ui.routes Its pages, each route with the file that draws it
ui.workers Web Workers its pages start, each name with its script

mod info on any installed module shows the range it asks for under Core API, followed by the core API this EiN provides, which system-info also shows on its api line. A module without coreApi still installs, with a warning.

Add a command in bash

A file in bin/ that starts with #!bash is a command written in EiN's shell language. The arg builtin declares its arguments, which gives it --help, Tab completion and an entry in the command reference, the same as EiN's own commands. Write bin/recipe-add:

#!bash
arg --desc "Add a recipe"
arg --effect write
arg '<title>' string "The dish, as the family calls it"
arg -s --serves number "How many it serves"
arg --example "recipe-add 'Apple cake' --serves 8"
arg --returns "nothing; the recipe node is created."
arg --export

name=$(echo "$TITLE" | tr ' ' '_' | tr -cd 'A-Za-z0-9_-')
mknode -t recipe "/archive/recipes/$name" --as "title=$TITLE" --as "serves=$SERVES" || exit 1
echo "added /archive/recipes/$name"

arg --export reads the arguments and sets $TITLE and $SERVES. A command run this way runs with the access of whoever runs it, like any script. The shell language lists every form arg takes.

Say what the command does to the system with arg --effect read or write. With the Assistant installed, the assistant runs a read command at once and shows a write to the person first; a command that says nothing is treated as a write.

Add a command in TypeScript

A file in bin/ that starts with #!ts is a TypeScript command. Its default export is a function that takes the command object and returns an exit code, and carries a spec that describes it. Write bin/recipe-list:

#!ts
import type { CmdReturn, Command } from '@ein/client';

const ROOT = '/archive/recipes';

const recipeList = async (cmd: Command): CmdReturn => {
  const entries = await cmd.sys.vfs.children(cmd.access, ROOT).catch(() => []);
  const recipes = entries
    .filter((entry) => entry.node.type === 'recipe')
    .map((entry) => ({
      path: `${ROOT}/${entry.name}`,
      title: String(entry.node.attrs.title ?? entry.name),
      serves: String(entry.node.attrs.serves ?? ''),
    }));

  if (cmd.json) await cmd.writeJSON(recipes);
  else for (const recipe of recipes) await cmd.writeLn(`${recipe.title}  (serves ${recipe.serves || '?'})`);
  return 0;
};

recipeList.spec = {
  name: 'recipe-list',
  effect: 'read' as const,
  description: 'List the recipes, with how many each serves',
  args: [],
  flags: [],
  examples: ['recipe-list'],
  returns: 'One entry per recipe: path, title and serves.',
};

export default recipeList;

A #!ts command runs inside EiN's own process, with all of its permissions. EiN therefore runs one only from a module under /usr/modules, where only the administrator can put files. The same file anywhere else, a home folder included, stops with a #!ts command runs only from a module in /usr/modules and status 126. A person's own commands are bash scripts.

Module code imports from core only @ein/client, the module API. What a command uses most:

Member What it is
cmd.args The words after the command's name; read flags from them with parseArgs
cmd.json True when the caller wants JSON, as the Web UI and JSON_OUTPUT=1 do
cmd.writeLn, cmd.writeJSON, cmd.writeError Write a line, a JSON answer, or a line on stderr
cmd.stdin Standard input: for await (const line of cmd.stdin.lines()), or all of it with cmd.stdin.text()
cmd.execute(script, { stdin }) Run a shell line and get its code, stdout and stderr; quote paths with shq, and pass text as stdin
cmd.progress(fraction) Say how much of the work is done, 0 to 1; a pipeline step shows it under Ongoing, and it keeps it off quiet
cmd.sys.vfs The tree, read and written with cmd.access, the caller's access: nodes, their content, queries and searches
cmd.env, cmd.cwd The caller's environment, settings included, and working folder
cmd.interrupted, cmd.onInterrupt Whether the person pressed Ctrl+C, and a handler for it

And the parts of spec:

Field What it says
name The command's name, the same as the file's
description What it is for, in one line, for --help, the command reference and the assistant
args Each positional argument: name, type (string, path, user, group, command, number, subcommand) and description
flags Each flag: name, type (bool for a switch) and description
effect read or write; a reading command marks the arguments or flags that make it a write with writes
examples One or two real command lines
returns What it answers with under JSON_OUTPUT=1, in a sentence
admin true when only an administrator may run it; for anyone else it is left out of completion and the reference
json false for a command that writes text even when JSON is asked for

A command may import packages through the manifest's imports, such as "@std/path": "jsr:@std/path@^1.1.3", and files of its own through aliases named after the module, such as "@recipes/store": "./lib/store.ts". A file outside the module is reached only through another module's exports (see Use another module).

Try the module on your EiN

With the standard installation, EiN keeps the modules it installs in modules/ in its data folder, ~/ein/data/modules unless you chose another data folder, which EiN sees as /var/lib/modules.

  1. Put the module's folder there under the module's name, and make its commands executable:

    # on the machine EiN runs on
cp -r ~/src/module-recipes ~/ein/data/modules/recipes
chmod 755 ~/ein/data/modules/recipes/bin/*

  2. Link it among the installed modules and set it up:

    # in EiN's terminal, as the administrator
ln -s /var/lib/modules/recipes /usr/modules/recipes
mod setup recipes

    Setup says what it did, with lines like these:

    Setting up module 'recipes'...
  roots: /archive/recipes
  Added /usr/modules/recipes/bin to PATH
  Linked navigation at /etc/ui/nav.d/recipes.json
Module 'recipes' setup complete
  recipes: built, 3.1 KB in 820 ms

    The last lines come from bundling every module's pages, one line per module.

  3. Try the commands. mod setup added bin/ to PATH in /etc/bashrc, which every shell reads again before its next command, an open terminal tab included:

    # in EiN's terminal
recipe-add "Peggy Wrenfield's apple cake" --serves 8
recipe-list
recipe-list --help

  4. Reload the web page. Settings → Modules lists recipes as Active, and its panel shows what it brings.

Restarting EiN does step 2 for you: at every start EiN links each folder in /var/lib/modules that has a mod.json and sets every module up, in the order of their dependencies.

Warning

mod remove recipes deletes a module's folder in /var/lib/modules along with its link. Keep your working copy, and its git history, somewhere else and copy it in.

Change it and see the change

What you have to do after an edit depends on what you changed:

You changed To see it
A file in bin/ Nothing: the next run uses it
A file in lib/ that a #!ts command imports mod setup recipes, which drops the commands EiN has loaded
mod.json: settings, node types, roots, indexes mod setup recipes
A new file in services/ or pipelines/ mod setup recipes, then service start <name> for a new service
A page, or anything it imports ui-build recipes, then reload the web page
ui/nav.json Reload the web page

EiN keeps a loaded TypeScript command against its file alone, so an edited lib/ file reaches a command when the command's own file changes, after mod setup, or after EiN restarts.

Add a page and a sidebar entry

A module's pages are React components. EiN bundles them itself, from the module's files, whenever modules are set up; there is no build step on your side and nothing is fetched from the network.

  1. Name each route and the file that draws it in mod.json, as above: "ui": { "routes": { "/recipes": "ui/pages/recipes.tsx" } }. A route is a path below /, of literal and :param segments, such as /recipes/:name.

  2. Write the page. Its default export is the component:

    import { Stack, Table, Title } from '@mantine/core';
import { EmptyState, PageLoader } from '@ein/ui/components';
import { useCommand } from '@ein/ui/hooks';

type Recipe = { path: string; title: string; serves: string };

export default function Recipes() {
  const { data, loading, error } = useCommand<Recipe[]>('recipe-list');
  if (loading) return <PageLoader />;
  if (error) return <EmptyState title='Recipes could not be read'>{error.message}</EmptyState>;
  if (!data?.length) return <EmptyState title='No recipes yet'>Add one with recipe-add.</EmptyState>;
  return (
    <Stack>
      <Title order={2}>Recipes</Title>
      <Table>
        <Table.Tbody>
          {data.map((recipe) => (
            <Table.Tr key={recipe.path}>
              <Table.Td>{recipe.title}</Table.Td>
              <Table.Td>{recipe.serves}</Table.Td>
            </Table.Tr>
          ))}
        </Table.Tbody>
      </Table>
    </Stack>
  );
}

    useCommand runs a command in the reader's own shell, as JSON, and keeps its answer. A page reads and changes the tree only through commands, which is why each part of a module that the Web UI shows has a command behind it.

  3. Give it a sidebar entry in ui/nav.json:

    {
  "sidebar": [
    { "id": "recipes.list", "section": "browse", "label": "Recipes", "icon": "tools-kitchen-2", "to": "/recipes", "order": 60 }
  ]
}

  4. Run ui-build recipes and reload the web page. Recipes is in the sidebar's Browse section.

A page imports only what the Web UI lends it, its own files, and anything at all with import type:

Import What it is
react, react-dom React, the one the Web UI runs
@mantine/core, @mantine/dates, @mantine/hooks The Mantine components the interface is built with
react-router-dom Routing: Link, useParams, useNavigate, useSearchParams and the like
@preact/signals-react, @hello-pangea/dnd Signals, and drag and drop
@ein/ui/components, @ein/ui/hooks, @ein/ui/lib, @ein/ui/signals, @ein/ui/theme The interface's own parts
@ein/paths Core's path names
Your module's files, CSS and CSS modules included By relative path or through its imports
A script EiN serves, by its path: import('/file/usr/modules/recipes/glue.js') Not bundled; the browser loads it when the import runs

Anything else stops the build with a message naming the file and the import.

A page writes a date or a time with formatDateTime, formatDate or formatTime from @ein/ui/lib, which take the options toLocaleString takes, or with dateTimeFormat where it needs an Intl.DateTimeFormat. They follow the reader's Date and time format; toLocaleString and a bare Intl.DateTimeFormat follow the browser's language instead, which gives an English browser a 12-hour clock. deno lint refuses those in a page (the rule ein/ui-date-locale): toLocaleDateString, toLocaleTimeString, toLocaleString on what reads as a date, and an Intl.DateTimeFormat without a locale. A number's toLocaleString() stays allowed.

Where an entry opens a route

A module gives the Web UI entries and routes, nothing more. Each entry says where its route opens:

Entry Where it appears
sidebar In a section of the sidebar (main, explore, browse, system); needs section, label, icon and to
topbar A button in the top bar, or a row of a dropdown it names as parent, such as ui.create, the Create menu
panels Inside another page, at a slot it names, such as system.tabs (a tab of the Status), device.tabs (a tab of a device's page), nodes.tools or settings.views (a page under Set up on Settings)

A top-bar entry's action is { "navigate": "/recipes" } for the page, { "dialog": "/recipes/new" } for the dialog over it, { "drawer": … } for the side drawer and { "fullscreen": … } for over everything; { "run": … } runs a command line instead, and with navigate beside it goes where the command's answer says. Each entry's id is <module>.<name>. icon is a Tabler icon name. admin: true shows an entry to administrators only, signedIn: true to people who are signed in, group: "<group>" to that group's members and administrators, and app: true only in the EiN app for Android, never in a browser. ui-nav prints the navigation as the reader gets it, with a warning for each entry it left out and why.

The administrator and each person can move, rename and hide a module's entries; Your sidebar and top bar shows how.

To make nodes of your type into links wherever EiN shows them, in search results, completions and the node explorer, name the route that opens one in mod.json: "ui": { "open": { "recipe": "/recipes/{name}" } }. {name} is the node's last path segment, {parent} the one before it and {path} its whole path. Files of your own under a folder open the same way by the folder: "/etc/things/": "/things/{rest}" (ui.open).

A page that draws something to drag and zoom, as a map or a diagram, takes the gestures from usePanZoom in @ein/ui/hooks: dragging, pinching, the wheel about the cursor and a double tap, with ignore for what on the drawing keeps a press to itself, such as a card dragged on it. The family tree draws with it, and so does the Automation module's graph.

A Web Worker for a page

Work that would stall the page, such as a solver, a decoder or a program compiled to WebAssembly, runs in a Web Worker. Name the worker and its script in mod.json (ui.workers):

"ui": {
  "routes": { "/solver": "ui/pages/solver.tsx" },
  "workers": { "solver": "ui/solver/worker.ts" }
}

The script runs in the worker. It may import your module's own files and what the modules it depends on export, but nothing the Web UI lends a page: a worker has no React, Mantine or @ein/ui/*.

// ui/solver/worker.ts
import { solve } from './solve.ts';

declare const self: DedicatedWorkerGlobalScope;

self.onmessage = (event: MessageEvent<string>) => self.postMessage(solve(event.data));

The page starts it with moduleWorker from @ein/ui/lib, by your module's name and the worker's, which gives a Worker of type module; the options are a Worker's, name among them, without type. It throws when the module has no worker of that name, for example before ui-build has run since the field was added.

import { useEffect, useState } from 'react';
import { moduleWorker } from '@ein/ui/lib';

export default function Solver() {
  const [answer, setAnswer] = useState('');
  useEffect(() => {
    const worker = moduleWorker('recipes', 'solver');
    worker.onmessage = (event: MessageEvent<string>) => setAnswer(event.data);
    worker.postMessage('2 + 2');
    return () => worker.terminate();
  }, []);
  return <p>{answer}</p>;
}

The worker reads files from EiN as the person on the page, with their session: fetch('/file/…'), an XMLHttpRequest, synchronous too, for a byte range of a file (Range: bytes=0-1023), and import('/file/usr/modules/recipes/…') for a script the module keeps outside the build, such as a program's JavaScript glue. It may compile WebAssembly, and draw on an OffscreenCanvas the page hands it. deno task check checks a TypeScript worker with the webworker library instead of the dom one a page gets, so document is an error in it and FileReaderSync is not.

Add a setting

A module owns settings by listing them in mod.json under config.options. Setup adds them to Settings and config; the values live in /etc/config and each person's ~/.config, and every shell sees them as environment variables.

"config": {
  "options": [
    {
      "key": "CFG_RECIPES_DEFAULT_SERVES",
      "scope": "system",
      "type": "number",
      "default": "4",
      "label": "Servings when none is given",
      "description": "How many a recipe serves when it was added without saying.",
      "group": "Recipes"
    }
  ]
}

A command reads it as $CFG_RECIPES_DEFAULT_SERVES, or cmd.env.CFG_RECIPES_DEFAULT_SERVES. A user setting is named CFG_USER_…, and a key to another service is a secret named CFG_…_KEY, which no shell sees. The module manifest lists every key of an option, and Configuration explains how the values are layered.

A module that wants a setting, its own or core's, to have a value of its choosing writes it in etc/config, as export KEY='value' lines. Setup links the file as /etc/config.d/<name>; a value the administrator sets wins over it. The ems module's names its text embedder this way:

export CFG_TEXT_EMBEDDER='ems-text-embed'

Give a settings view

Settings that belong together, such as a service's address and its key, are easier to set up on a page of their own than one by one in their category. A module gives such a page as a route and a settings.views panel in ui/nav.json; Settings → System lists it under Set up, before the categories, and the module's own Settings tab under Settings → Modules shows it before its settings. description is the line under its name:

"panels": [
  {
    "id": "recipes.source",
    "slot": "settings.views",
    "label": "Recipe source",
    "description": "Where new recipes come from, and the key it takes.",
    "icon": "chef-hat",
    "route": "/settings/recipe-source",
    "admin": true
  }
]

The page reads the settings with useConfig('system') from @ein/ui/hooks and saves them with its saveAll({ KEY: 'value', … }) or resetAll([KEY, …]), one config set KEY=VALUE… or config unset KEY…: all are checked before any is written, and a service that reads several restarts once. SaveBar and useViewSave from @ein/ui/components give it the Save and Cancel every such page has and say what the save restarted or why it failed; settingOf picks one setting from the table, and SettingSource draws its badge. It saves only what it changed, so a setting left alone keeps its source. The page and the categories read the same settings, and a save through either is seen by the other at once.

Run something in the background

A service is a script EiN keeps running: a folder services/<name>/ with a start.sh and a config.json. Setup registers it, and enables it the first time it does: an administrator who disables it keeps it disabled. EiN starts the enabled services when it starts, and service start <name> starts one now.

{
  "description": "Checks the recipes every hour",
  "restartPolicy": "on-failure"
}
# services/recipe-check/start.sh
while true; do
  recipe-list > /dev/null
  sleep 3600
done
Key What it does
description One line for the Status's services and service list
restartPolicy on-failure, always or never; with a restart policy EiN starts a failed service again
maxRestarts How many restarts within restartWindow before the service stays failed; 3 by default
restartWindow That window, in milliseconds; 60000 by default
stopTimeout How long a stopping script may take before it is closed, in milliseconds; 5000 by default
env Environment variables for the script
statusCommand A command answering the service's health in one line, shown beside its status
checkCommand A command answering checks for health, as JSON [{ name, state, reason }] with ok, warn or fail
gaugeCommand A command answering meters for top and the Status, as JSON [{ label, percent?, value }]
workClass background for a service whose work may wait behind people's: its database connections leave some free for them

Module services use "restartPolicy": "on-failure". A service whose name the module stops shipping is stopped and removed at the next setup. Services and logs shows where a service's output goes.

Talk live with a page

A module's service and its pages can talk while both run, such as a game several people play or a board they draw on at once, through two node types of which nothing is kept:

  • A socket is a conversation: the service listens on it, and each page connects to it, each connection carrying messages both ways between that page and the service alone.
  • A stream is live bytes from one writer to any number of readers, such as a camera's video.

A page holds either open over a WebSocket at the node's address under /file/, with openNodeSocket(path, mode) from @ein/ui/lib, which gives a WebSocket on the page's own host, ws: or wss: as the page is, with its messages as ArrayBuffers. The service opens the same node as it opens a file.

A conversation: a socket

The service makes the socket where its pages find it, open to the accounts that may join, and listens on it:

# in EiN's terminal, or the service's setup
mknode -t socket -m 0666 /tmp/recipes/board
import { isSocketListener, type SocketConnection } from '@ein/client';

const listener = await cmd.sys.vfs.open(cmd.access, '/tmp/recipes/board', { mode: 'r' });
if (!isSocketListener(listener)) throw new Error('not a socket');
for (let connection = await listener.accept(); connection; connection = await listener.accept()) void answer(connection);

// Answers each message with itself, until the page leaves.
async function answer(connection: SocketConnection) {
  for (let message = await connection.read(65536); message.length > 0; message = await connection.read(65536)) await connection.write(message);
}

The page connects with rw:

import { NODE_SOCKET_CLOSE, openNodeSocket } from '@ein/ui/lib';

const board = openNodeSocket('/tmp/recipes/board', 'rw');
board.onopen = () => board.send(new TextEncoder().encode('hello'));
board.onmessage = (event) => show(new Uint8Array(event.data));
board.onclose = (event) => {
  if (event.code === NODE_SOCKET_CLOSE.ended) startOver();
};
  • Who listens: the socket's owner, or an administrator, opening it to read. A socket has one listener at a time; another is refused. A module's service runs as the administrator, so it listens on any socket it makes.
  • Who connects: an account that may both read and write the socket, at /file/<path>?mode=rw, or with any mode that writes when it opens the node itself (vfs.open with mode: 'w'). While nobody listens the socket is closed with 4503.
  • accept answers each connection in turn, and undefined once the listener is closed or the node removed. A connection's peer says who opened it: the account's uid and gid, and the invitation it came through (below).
  • Messages are binary, at most 8 MiB each, and arrive whole, each send one message and each read one message when its size holds it. What a page sends before the service accepts it waits in its connection.
  • Nobody waits for the other end. An end that falls more than 8 MiB behind lets the connection go: the page's socket closes with 4001.
  • Either end closing ends the connection: the page's close makes the service's read answer an empty message, and the service's close closes the page's socket with 1000. Closing the listener, or removing the node, ends every connection.

One writer, many readers: a stream

A stream carries one direction: the service writes it and every page reading it is given what it writes from then on, or a page writes it for the service to read.

# in the service: the board's moves, for everyone watching
mknode -t stream -m 0644 /tmp/recipes/moves
const moves = openNodeSocket('/tmp/recipes/moves', 'r');
moves.onmessage = (event) => show(new Uint8Array(event.data));
  • mode=w: the socket is the stream's writer for as long as it is open. Each binary message is one write, and closing the socket ends the stream for its readers. A stream has one writer at a time: a second socket is closed with 4409.
  • mode=r: each write comes as one binary message. A reader starts at the moment it opens, or at the latest point the writer marked as a start; what came before is gone. The writer's close closes the reader's socket with 1000, and the reader opens it again to go on.
  • Messages are binary, and at most 8 MiB each. A reader is given each write whole, so between a page writing over a socket and a page reading over one, a message arrives as it was sent. A writer that writes in pieces of its own, such as cat or a program over SFTP, may pass on several messages as one write or one as several: give the messages a frame of your own, such as a length before each, when they pass through one.
  • Nobody waits for a reader. A reader that falls more than 8 MiB behind is given what it holds and then closed with 4001.
  • A stream is read or written, never both: a conversation is a socket.

Who may open them, and how they end

Who may open either is decided as for any /file/ address: as the account signed in, with the node's own permissions, and only from EiN's own pages; a page from any other address cannot use the sign-in. A file ticket (?ticket=) reads a stream instead, and never writes, and an invitation (?invite=) opens its own nodes from a page at any address (below). nodeSocketUrl(path, mode) gives a socket's address without opening it. Any other node type is refused.

What could not open, and how a socket ended, is in its close code, with a reason a page can show. All of them are in NODE_SOCKET_CLOSE:

Code NODE_SOCKET_CLOSE What happened
1000 ended The stream's writer closed, the node was removed under a reader, or the connection ended
1001 EiN is stopping
1003 unsupported A text message, or a message from a stream's reader
1009 tooBig A message over 8 MiB
1011 failed Something failed in EiN
4001 behind The reader, or one end of a connection, fell more than 8 MiB behind
4400 badRequest No mode, a mode the node does not open with, or a node that is neither a stream nor a socket
4401 signIn Not signed in, where visitors may not browse
4403 forbidden The account may not open the node in that mode, or the ticket or invitation does not open it
4404 notFound Nothing at the path
4409 conflict The stream has a writer already
4410 gone The node was removed under its writer, or the invitation expired or was turned off
4503 unavailable Nobody listens on the socket, or too many connections wait for its listener

Someone with no account here

Someone without an account here, or a page served by another EiN, takes part through an invitation: a token that opens the nodes it names, a socket to connect to or a stream to read or to write, as the account that made it, until it expires or is turned off. The service makes one when someone is invited, and hands its link to whoever invites them:

# in the service: someone from elsewhere is invited to the board
invitation create --connect /tmp/recipes/board
# /__invite/Xq3…  opens rw /tmp/recipes/board until …

It works for 24 hours unless --expires says otherwise. With JSON_OUTPUT=1 in front it answers the token, the link and the nodes as JSON. Either way it gives the token once: only a hash of it is kept. Put the server's own address in front of the link, https://ein.example/__invite/Xq3…, and send that. A page that is handed it, on this EiN or another, asks the link what it opens and opens each node with the token instead of a sign-in:

import { fetchInvitation, openNodeSocket } from '@ein/ui/lib';

const invitation = await fetchInvitation(link);
const sockets = invitation.nodes.map((node) => openNodeSocket(node.path, node.mode, { origin: invitation.origin, invite: invitation.token }));

fetchInvitation reads GET <origin>/__invite/<token>, which answers a page at any address with the nodes and the expiry, { "nodes": [{ "path": …, "mode": "rw" }], "expires": "2026-…Z" }, or 404 once the invitation opens nothing; parseInvitationLink splits a link into its EiN and token without asking. The socket is wss://ein.example/file/<path>?mode=<mode>&invite=<token>: on it EiN reads no cookie and does not ask which page it came from, and opens only the invitation's nodes, each in its own mode. A connection made with it is its maker's, and its peer.invitation is the invitation's id, so the service can tell a guest from the maker. When the invitation expires or is turned off, its sockets close with 4410.

openNodeSocket, nodeSocketUrl and NODE_SOCKET_CLOSE came with core's module contract 0.15.71; invitations, fetchInvitation, parseInvitationLink and openNodeSocket's origin and invite with 0.15.73; and socket nodes, isSocketListener, isSocketConnection and rw with 0.15.74: give a module that uses them "coreApi": "^0.15.74".

With the Games module installed, the Games page shows a card for each game the installed game modules have, and plays each on a page that is the same for every game. The engine in a worker

A game's engine runs in a Web Worker of its module, not on the page: there it may read the game's files a piece at a time as it asks for them, with synchronous range requests, and a slow frame does not stall the page. Games gives both ends, so start is one call. The engine has a platform layer of its own, as doomgeneric's is, and not SDL: SDL's browser port listens to the page's DOM events, which a worker has none of. Everything between the two goes by postMessage, frames and sound transferred rather than copied, and nothing is shared memory: EiN's pages are not cross-origin isolated, so neither a page nor a worker has SharedArrayBuffer.

Name the worker in mod.json (A Web Worker for a page):

"ui": {
  "routes": { "/rover/:game": "ui/pages/play.tsx" },
  "workers": { "engine": "ui/rover/engine-worker.ts" }
}

What the engine is started with is the module's own, in a file both ends import:

// ui/rover/start.ts
/** What the engine's worker is started with. */
export type RoverStart = { glue: string; wasm: string; args: string[] };

The worker is type-checked without the DOM, so a file it imports, even for a type, imports neither @ein/ui/* nor @games/worker nor the page's own files.

start.payload The module's own start message for its engine: its build's URLs, its command line, whether it plays its demos. The worker has it as boot.payload
start.lazy Files the engine reads from EiN as it asks: each its path in the engine's file system, its url (fileUrl of its EiN path) and its size, which EiN is asked for when not given
start.files Files the engine is given whole, each its path and its bytes: small ones, and the player's kept files
start.music The game's music, { folder, tracks }, the file of each track by its number, which the page plays when the engine asks
start.controls(post) The game's key, button and wheel, and optionally mouse and step: what each posts to the engine, { type: 'key', pressed, key }, char, mouse, button, or { type: 'input', data } for anything else. step runs before each tick
options sound, log, onKeep and online of the StartOptions, as start was given them

keyControls(post, { key, button, wheel }) is the controls of an engine that takes everything as its keys: key(code) and button(button) give the engine's number for a key or a mouse button, or nothing for one it does not take, and the wheel presses and lets go of its two keys. A game whose engine wants a gamepad posts its buttons from step, since a worker cannot read gamepads. fetchFile(path) fetches a file of EiN's whole, for files.

Each animation frame the page sends the worker a tick, with the datagrams that came for the game's sockets, and never a second before the first is answered; it paints the frame the answer carries, and menu() and fullscreen() say what the answer said. The sound the engine mixes is played from a queue of at most 0.2 s, which starts once a little more than the page plays at a time is waiting. keep(), disconnect() and setFullscreen() are posted, and stop() ends the worker once it has done what it was asked before. A game that fails to start throws, with the error the worker gave, and Quit ends it as quitted recognises.

The worker hands its engine to serveEngine from @games/engine, which answers the page:

// ui/rover/engine-worker.ts
import { argv, type EmscriptenModule, type Engine, FrameCanvas, heapSound, keptPath, serveEngine, startEmscripten } from '@games/engine';
import type { RoverStart } from './start.ts';

/** What the engine's platform layer exports, beside Emscripten's own. */
type RoverModule = EmscriptenModule & {
  _ein_start(argc: number, argv: number): void;
  _ein_tick(): void;
  _ein_key(pressed: number, key: number): void;
  _ein_frames(): number;
  _ein_screen(): number;
  _ein_width(): number;
  _ein_height(): number;
  _ein_audio_rate(rate: number): void;
  _ein_audio_render(at: number, frames: number): void;
  _ein_write_config(): void;
};

let rover: RoverModule;
let drawn = 0;
const frames = new FrameCanvas();
let sound: ((count: number) => Int16Array<ArrayBuffer>) | undefined;

const engine: Engine<RoverStart> = {
  async boot(boot) {
    rover = await startEmscripten<RoverModule>(boot, boot.payload, {
      // `./rover/rover.cfg` is the player's rover.cfg, in /home.
      written: (path) => ({ path: `/home/${keptPath(path, 1)}`, name: keptPath(path, 1) }),
    });
    if (boot.sampleRate) {
      rover._ein_audio_rate(boot.sampleRate);
      sound = heapSound(rover, (at, count) => rover._ein_audio_render(at, count));
    }
    rover._ein_start(boot.payload.args.length, argv(rover, boot.payload.args));
  },
  tick: () => rover._ein_tick(),
  frame() {
    if (rover._ein_frames() === drawn) return undefined;
    drawn = rover._ein_frames();
    const [width, height] = [rover._ein_width(), rover._ein_height()];
    return frames.rgba(new Uint8Array(rover.HEAPU8.buffer, rover._ein_screen()), width, height);
  },
  sound: (count) => sound?.(count),
  key: (pressed, key) => rover._ein_key(pressed ? 1 : 0, key),
  keep: () => rover._ein_write_config(),
};

serveEngine(engine);

An Engine is the module's; boot, tick and frame are required:

Member What it is for
boot(boot) Load the engine and start the game; the page hears it started once it resolves. boot has the payload, lazy, files, screen (the screen's size in its pixels), sampleRate when the game has sound, and the page's services, below
tick() Run the game on by a frame, or by the time since the last tick. It may answer a promise, as an engine under ASYNCIFY that waits for its next frame does: nothing else is called until it resolves
frame() The frame drawn since it was last asked, as an ImageBitmap; nothing when there is none new
sound(frames) The next frames frames of sound at sampleRate, interleaved 16-bit stereo. The worker asks at each tick for the time since the last, at most a quarter of a second
key, char, mouse, button Input as the page's controls posted it, in order, between ticks
input(data) Whatever else the controls posted as { type: 'input', data }
menu(), fullscreen(), setFullscreen(on) As the RunningGame's, read after each tick
keep() Write the player's settings: asked by the page as it stops the game or closes, and by the worker as a menu or the console closes, where settings change, since a tab that closes cannot wait for its worker
disconnect() Leave the hosted game

Anything boot or a tick throws ends the game, Emscripten's ExitStatus of 0 as Quit. The page's services on boot are log(line); keep({ files, folder }), files of the player's for onKeep; network, when the game plays online, with open(port) (0 for a free port), close, send(from, ip, to, data), recv(port) and waiting(port), as a Network's; music, when the page plays the game's music, a MusicSink; and end(error?), for an engine that ends outside a tick, as one whose main loop runs on its own does.

For an engine built with Emscripten, @games/engine has the rest. Build it as an ES module (-sMODULARIZE -sEXPORT_ES6) that does not run its main by itself (-sINVOKE_RUN=0), with FS and the heap views it uses exported, and keep the glue and the wasm in the module's files, outside the UI build:

Helper What it does
startEmscripten(boot, { glue, wasm }, options) Loads the glue and compiles the wasm from its bytes, gives Module the page's services where the platform layer calls them (print, printErr, einNet, einMusic, and einWrote(path) with options.written), puts lazy and files in its file system, and answers the module. options.canvas is the canvas the engine draws on with WebGL, options.module more of Module's options
lazyFile(fs, path, url, size?) A file of the engine's file system read from EiN a megabyte at a time, each piece fetched once with a synchronous range request
FrameCanvas The OffscreenCanvas frames come from: take() what the engine drew on canvas with WebGL, rgba(pixels, width, height) a frame of R, G, B, A bytes from the engine's memory
heapSound(module, render) An Engine.sound from a mixer that renders into the engine's memory
argv(module, args) A command line as a C program's argv
ChangedFiles, keptPath(path, skip) Which written files differ from what the page already has, so a settings file written again unchanged is not saved again; and a written path's name among the kept files, without its first folders

einWrote(path) hands the page the file the game wrote at path, when it changed, or a folder, a save slot, with all its files; written says where the path is in the file system and its name among the kept files.

Saves

What the game keeps of a player is in their home, ~/.rover/<game id>, a folder for each game, so a save is only ever loaded into the game it was made in. The page makes the folder, reads the files kept matches into StartOptions.kept before the game starts, and writes each onKeep hands it in the order the game wrote them. A save slot written as a whole ({ files, folder: 'save/s1' }) empties the slot's folder first. Files kept.shared matches as well are kept once for every game of the module, in ~/.rover itself: settings a player has whatever they play, as kept: { pattern: /^(rover\.cfg|save\/s\d+\/[^/]+)$/, depth: 2, shared: /^rover\.cfg$/ } keeps the key bindings in ~/.rover/rover.cfg. Someone not signed in keeps nothing.

Dropped files

Each rule in drops is tried on each thing dropped on the Games page, a file or a folder, in the browser, before anything is uploaded. Every condition a rule gives must hold, and it gives at least one of name, contains and magic:

Field What it is
place Where a match goes: module, into the module's folder as it was dropped, a folder by its name; own-folder, a file into a folder of its own in folder, named after the file without its extension (a game that is one file); game, into an installed game's path
label What the match is, in the chooser and the notice: a Star Rover map. Required
name A regular expression the file's or the folder's name matches, without regard to case
contains A dropped folder: the name of a file at its top, without regard to case
magic A dropped file: bytes it starts with, any one of a list of { "at": offset, "text": "RVR1" } (printable ASCII) or { "at": offset, "hex": "52565231" }
into With game: the folder under the game's path it goes into, such as maps
families With game: the families of the games that take it; every installed game of the module's when not given

A game rule is a place for each installed game it fits, and none when no game fits. When exactly one place holds for a thing, it is uploaded there; when several do, across rules, games and modules, or none, the person chooses: among those that hold, or, when none does, any module's folder and any installed game. Nothing starts by itself.

Playing together

A game is hosted, joined and stopped by Games' commands, the same for every module: games-host <module> <game> [map] --max N --mode M, games-servers, games-join <id>, games-invite <id> and games-stop <id>. A hosted game is a folder, /groups/users/games/servers/<module>/<id>, with its server.json (ServerInfo: its game, map, mode, who hosted it, its state and players) and one socket node, socket, which each player's page connects to with rw, or with an invitation from another EiN (Talk live with a page). The service that runs the module's games makes the module's folder, which is how games-host knows the service runs, and runs each game games-host asks for in it.

The drop-in's multiplayer says how:

Field What it is
modes The ways a game is hosted, { "value", "label" }: value is what the module's server takes, label what the page says. The first is the default
maxPlayers The most players a game is hosted for, from 2
defaultPlayers The players a host is offered first, from 2 to maxPlayers
defaultMaps The maps offered first, in order, when a game has them; else its first
transport server, the players play against a server the module's own service runs; relay, they play peer to peer, through Games' games-relay

Either way a link carries one datagram in each message. The engine's socket layer hands its datagrams to a Network from @games/net in place of UDP, and reads them from it: open(port) (0 for a free port), close(port), send(from, ip, to, data), recv(port), which answers { ip, port, data } or nothing, and waiting(port). An address is one number, as addressNumber('10.66.0.1') and addressText turn it. A socket keeps 256 datagrams unread before it drops the oldest, and a datagram for nobody is dropped, as UDP drops it.

Against a server

Each message is a frame: the port the datagram is from and the port it is for, two bytes each, big-endian (FRAME_HEADER, 4 bytes), then its bytes, at most 65,535. frame(from, to, data) and unframe(message) make and read one. A player sees the server at SERVER_ADDRESS, 10.66.0.1, which is online.address: the page's Network sends every datagram up the link, whatever address it is for, and gives every one that comes down as from that address.

The module's own service runs its games with GameServers from @games/host and a ServerEngine of its own. The service is a command with admin: true and daemon: true in its spec, run by services/rover-server/start.sh:

#!ts
/** rover-server — the rover-server service: runs every hosted Star Rover game until it is stopped. */
import type { CmdReturn, Command } from '@ein/client';
import { GameServers } from '@games/host';
import { roverEngine } from '@rover/server';

const roverServer = async (cmd: Command): CmdReturn => {
  const stopped = new Promise<void>((resolve) => cmd.onInterrupt(resolve));
  await new GameServers(cmd, ['rover'], roverEngine()).run(stopped);
  return 0;
};

roverServer.spec = {
  name: 'rover-server',
  admin: true,
  daemon: true,
  effect: 'write' as const,
  json: false,
  description: 'Run the Star Rover games hosted here (the rover-server service)',
  args: [],
  flags: [],
};

export default roverServer;

Its start.sh is the one line rover-server, and its config.json says what it is and how to count what it runs, as Games' own games-relay does:

{
  "description": "Runs the Star Rover games hosted here",
  "restartPolicy": "on-failure",
  "statusCommand": "games-servers --module rover --count"
}

GameServers does everything but the game: it makes the module's folder and empties it as it starts, starts each game whose server.json says starting and marks it running once it runs, stops one asked to stop (games-stop leaves a stop file in its folder) or whose folder has gone, stops one nobody has played for five minutes, and keeps a failed one listed for a minute with why. It makes each game's socket and listens on it. Whoever connects sits down at an address of the game's, 10.66.0.2, 10.66.0.3 and on (playerAddress(n)), kept by their seat's name, the account's or guest for an invitation's, with -2, -3 for another of the same, so a player who reloads the page is the same player to the game. It gives the engine every frame a player sends with their address, and sends every frame the engine gives for an address down that player's link.

type ServerEngine = { start(info: ServerInfo, io: ServerIo): Promise<HostedGame> };
  • start resolves once the game runs, within two minutes, or rejects with why it did not start, which games-host and the page say. Run the game in a worker, so a slow frame never holds up EiN.
  • HostedGame is deliver(ip, frame), a frame a player sent, the engine's to keep; seated(ip, seat), called before anything a new player sends, which answers why they may not play when they may not, and the service then closes their link; left(ip), their link closed; and stop().
  • ServerIo is what the game has of the service: send(ip, frame), log(line), ended(error?) when the game ends by itself, and status(map, players). Call status every few seconds with the map and who plays, each by their address, with name, frags and ping as the game knows them: it is written into server.json when it changed, and a game whose status has listed nobody for five minutes is stopped.

A server in a worker reads its players' datagrams while it runs without returning, when no message could reach it: the service writes each frame into a Ring (@games/net), memory the two share, and the worker's Network reads it in its pump, given as the second argument, before each read.

Through the relay

A module whose engine plays peer to peer needs no service: games-relay, Games' own, runs every relayed game with no game on the server, seats as many players as it was hosted for, and passes each datagram on. A relayed frame starts with an address, four bytes, big-endian, then is a frame as above (RELAY_HEADER, 8 bytes, then the datagram):

  • Up a link, from a player, the address is whom the datagram is for: another player's address, or BROADCAST_ADDRESS, 255.255.255.255, for every other player. The relay drops a datagram for any other address, its sender's own included.
  • Down a link, to a player, the address is whom it is from. The ports and the bytes are passed on as they came.

The relay's own word is JSON, in a frame from SERVER_ADDRESS, port CONTROL_PORT (0), to port 0, where an engine's sockets never are (RelayControl):

{ "type": "roster", "you": "10.66.0.3", "players": [{ "address": "10.66.0.2", "seat": "anna" }, { "address": "10.66.0.3", "seat": "olle" }] }
{ "type": "refused", "reason": "the game has room for 4 players, and that many play" }

Every player is sent the roster when they sit down, with their own address as you, and again whenever someone sits down or leaves. It lists every player, them too, by address, in the same order for everyone, so peers that number their players agree on the numbers. A player the game has no room for is sent refused, and their link is closed.

The page gives a relayed game's engine a RelayNetwork as online.network, and the relay's SERVER_ADDRESS as address. Once the first roster has come, which the page waits for before it starts the game, self is the player's own address and players who plays, seated has settled, and onRoster(listener) hears each later roster. send sends each datagram to the address it is for, or BROADCAST_ADDRESS; one to the player's own address comes back without leaving, and recv gives each with the address it is from. relayFrame, unrelayFrame and controlFrame make and read the frames, for an engine or a test that speaks to the relay itself.

Write documentation for it

A module's documentation in EiN comes from what it already declares: each command's spec or arg lines, each setting's label and description, and in mod.json its nodeTypes and the environment variables it reads other than its settings, under environment. docs commands, docs node-types and docs env read them from the installed modules, and so do the reference pages of this site.

A guide for the people who use the module, written for them rather than for developers, goes in its repository, beside mod.json. The modules published with EiN have theirs here, in this site's Modules part, which EiN carries offline in Documentation.

Use another module

A module shares files by naming them in exports, and another module imports them only if it lists the first in dependencies:

"dependencies": { "archive": "^0.1.0" }

With that, recipes may import what the Archive exports, as @archive/<name>, and run its commands. Nothing else of the Archive's is reachable. A dependency is checked at setup: it must be installed, at a version in the range, and it is set up first. mod install installs a missing dependency along with the module. mod info archive lists what the Archive exports and which installed modules depend on it.

To share your own files, export them: "exports": { "./api": "./lib/api.ts" } is imported elsewhere as @recipes/api. By convention ./api holds the types of what your commands answer as JSON, imports nothing but other such files, and is what your own pages import too.

Your pages may import a dependency's exports too, components and code as well as types: the exported file and what it imports are bundled into your pages, so a page of yours can be drawn by another module's component, as a game module's is. When that module is updated, your pages are bundled again with it. This came with core's module contract 0.15.75: give a module that does it "coreApi": "^0.15.75".

Test it

A module's tests run inside a checkout of core, with the module in its modules/ folder; see Building from source. There, deno task sync:modules writes the module's deno.jsonc from its mod.json (never edit that file), deno task check type-checks it, and deno task test:one modules/recipes/test/ runs its tests.

A test imports @ein/testing and runs commands in an EiN with the module set up:

import { assertEquals } from '@std/assert';
import { createTestContext } from '@ein/testing';

const testCtx = createTestContext({ modules: ['recipes'], boot: true });

Deno.test({ name: 'recipes', sanitizeResources: false, sanitizeOps: false }, async () => {
  await testCtx.setup();
  const client = await testCtx.server.createShellClient();
  await client.exec("recipe-add 'Apple cake' --serves 8");
  const recipes = await client.execJson<{ title: string }[]>('recipe-list');
  assertEquals(recipes.map((recipe) => recipe.title), ['Apple cake']);
});

The tests in core check what every module must keep to: a module imports from core only @ein/client, @ein/api, @ein/paths and, in pages, the interface's parts, and runs another module's commands only when it depends on it.

Publish it

  1. Push the module to a repository named module-recipes, with mod.json at its top. Commit the commands with their execute bit (git update-index --chmod=+x bin/*): EiN installs each file with the mode the repository gives it.

  2. Release versions as tags v<version>, such as v0.1.0, and raise version in mod.json with each: the minor when you add something another module may come to rely on, the major when something they use changes. Without a ref, mod install takes the highest of them, and the default branch only while there is none.

  3. Install it on any EiN by its address, with a branch, tag or commit after @ if you want one:

    # in EiN's terminal, as the administrator
mod install https://forge.example:3000/wrenfield/module-recipes@v0.1.0

    EiN fetches the commit from the forge, checks the module as setup would, puts it in place, sets it up and starts its services.

  4. To let administrators install it by name, they add your organisation to Module sources, CFG_MODULE_SOURCES. Then mod install recipes finds it, mod search lists it and Settings → Modules offers Install and Update. Modules covers sources that need a token.

When EiN's module API changes in a way that breaks modules, a module whose coreApi range the new EiN does not satisfy is refused at setup with needs @ein/client ^0.5.0, this core provides 0.6.0. Publish a version written for the new API, with its coreApi raised. An EiN that is older than the API a release asks for still installs your module by name: mod install without a ref takes the newest release whose coreApi it satisfies.

Remove it

mod remove recipes asks before it removes anything, runs the module's uninstall.sh if it has one, then takes back what setup did: its commands leave PATH, its services are stopped and removed, its pipelines, settings, navigation and guide are unlinked, and its pages are rebuilt without it. The module's content stays: its roots under /archive, and the values of its settings in /etc/config, which come back if the module is installed again.
